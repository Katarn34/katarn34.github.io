Systems I built

01Inventory, crafting, interaction & equipmentRefactor · Technical Designer
Problem
These four systems had been built early in production, without a defined architecture or documentation. They were tightly coupled: any change in one of them created bugs everywhere else, so the team had stopped touching them.
What I did

I repaired the existing systems so the game kept working, marked the old code as DEPRECATED, then designed and rebuilt a scalable architecture for every new system and item.

Interaction driven by data. Each item carries Gameplay Tags describing what can be done with it. When a player interacts, the tag tells the system which interaction to run, and a Data Table provides the text to display for that type. A new item or a new interaction is a data entry, not new code.

Multiplayer-ready. I removed the single-player assumptions (Get Player Character with index 0, unsafe casts) so every system works with several players. Networking was handled by my mentor; I worked closely with him, producing test builds to catch programming errors and multiplayer issues early.

Impact

No more bugs: the systems stay stable whatever tests the Designers run.

New item in under a minute: duplicate an item’s Data Asset, fill in its data, place the item in the world with that Data Asset in its Details. Done.

New interaction text in about a minute: add a line for the tag in the interactions Data Table, or create a new tag if needed.

Easy to extend: new requests became simple to add, such as item-specific interactions in the inventory: hold to consume for some items, a single click for others.

02Action ObjectsC++ · tools for Designers
Problem
Item effects (abilities, consumables, equipment bonuses) needed a programmer each time. Designers couldn’t create or tune an effect on their own.
What I did

I designed Action Objects, an effect system with a C++ base. Designers create the effects they want and set any value each effect needs, directly on the item.

The key: using EditInlineNew and Instanced objects, the Details panel shows only the variables of the chosen effect type. No code, no unrelated fields.

Example: Modify Stat. Added to an item, it lets a Designer pick any stat through a Gameplay Tag, then restore or remove it, instantly or over a chosen duration. The same Action Object covers a health potion, a stamina drain or a poison.

Impact
Designers now create any gameplay effect they need on their own. 3+ Action Objects are in use today, each one reusable across every item.
03Enemy AI & Designer toolsGameplay Programmer intern
Scope
AI for 4 enemy types: 3 Behavior Trees and 30+ custom BT / EQS nodes, dynamic NavMesh and telegraphed attacks. Above all, I built the tools that let Designers and Level Designers shape that behaviour themselves, live during sprint reviews.
Patrol System
Select an AI in the level and a Patrol System section appears in its Details. Level Designers pick the exact points it patrols, choose between several patrol modes, and set the wait time at each point and its random variation.
Movement fallbacks
Level Designers can also place Target Points for the AI to move to. Without them, it moves freely; if it comes from a spawner, it roams the spawner’s territory to guard it. Every AI has a sensible behaviour, even with no setup.
3D perception tool
Unreal’s default AI Perception debug doesn’t show sight in verticality, which matters as soon as levels have height. I built an editor tool that draws the AI’s full 3D vision and lets Designers edit it, with the preview updating in real time in the editor.
Impact
These tools were used constantly by Designers and Level Designers to tune AI behaviour, without asking a programmer for each change.
04Training the teamAdoption
What I did
A tool is only useful if people use it: I trained the whole team on the new systems and documented them, so anyone could add items, interactions and effects on their own.
