Systems I built

01Inventory, crafting, interaction & equipmentRefactor · Technical Designer
Problem
These four systems had been built early in production, without a defined architecture or documentation. They were tightly coupled: any change in one of them created bugs everywhere else, so the team had stopped touching them.
What I did

I repaired the existing systems so the game kept working, marked the old code as DEPRECATED, then designed and rebuilt a scalable architecture for every new system and item.

Interaction driven by data. Each item carries Gameplay Tags describing what can be done with it. When a player interacts, the tag tells the system which interaction to run, and a Data Table provides the text to display for that type. A new item or a new interaction is a data entry, not new code.

Clean ownership, ready for several players. Every system knows who created what and who owns it, through proper references rather than shortcuts like Get Player Character with index 0 or unsafe casts. Today it runs in local split-screen, with one widget per player and the right Owning Player; networking was handled by my mentor, and I worked closely with him, producing test builds to catch programming and multiplayer issues early.

Impact

No more bugs: the systems stay stable whatever tests the Designers run.

New item in under a minute: duplicate an item’s Data Asset, fill in its data, place the item in the world with that Data Asset in its Details. Done.

New interaction text in about a minute: add a line for the tag in the interactions Data Table, or create a new tag if needed.

Easy to extend: new requests became simple to add, such as item-specific interactions in the inventory: hold to consume for some items, a single click for others.

02Action ObjectsC++ · tools for Designers
Problem
Item effects (abilities, consumables, equipment bonuses) needed a programmer each time. Designers couldn’t create or tune an effect on their own.
What I did

I designed Action Objects, an effect system with a C++ base. Designers create the effects they want and set any value each effect needs, directly on the item.

The key: using EditInlineNew and Instanced objects, the Details panel shows only the variables of the chosen effect type. No code, no unrelated fields.

Three C++ classes, everything else in Blueprint. The studio works almost entirely in Blueprint, so I kept the C++ minimal: an abstract action class, instanced inline in Data Assets, whose execute function has a C++ base and can be fully overridden in Blueprint (with access to the World from a UObject); a Blueprint Function Library that creates a live instance of an action from the Designer’s template; and an item Primary Data Asset holding the list of actions run when the item is used or consumed.

Example: Modify Stat. Added to an item, it lets a Designer pick any stat through a Gameplay Tag, then restore or remove it, instantly or over a chosen duration. The same Action Object covers a health potion, a stamina drain or a poison. Stats are read and changed through a Gameplay Tag on the component that owns them, which keeps the systems decoupled.

Impact
8 effects created in Blueprint so far, without touching the C++. The latest ones feed a Blueprint skill system, built this way rather than with GAS so the team could stay out of C++.
03Enemy AI & Designer toolsGameplay Programmer intern
Scope
The AI was my largest area on the project: 4 enemy types, plus the tools that let Designers and Level Designers shape their behaviour themselves, live during sprint reviews.
Enemies
  • Melee duelistBuilt for close combat: dodges hits, picks different attacks depending on how the player behaves, kicks, draws its sword, jump attacks. Strong anticipation and feedback so the player can read every action.
  • ArcherAlways keeps the right distance from the player while shooting, and moves through vertical spaces. Clear anticipation before each shot.
  • Swarm variantsSmall, weak melee enemies that charge in a straight line and get in the player’s way: some apply debuffs, some leave a debuff effect when they die, some hinder movement, one self-destructs.
Architecture

Inheritance first. Each enemy has its own AI Controller, all inheriting from a common base controller that configures perception once for everyone.

Modular Behavior Trees. 3 main trees and 5 reusable sub-trees, all on a shared Blackboard, so a behaviour written once serves several enemies.

Custom nodes. 30+ custom nodes: Tasks, Services, Decorators and EQS contexts.

EQS. 6 queries with custom contexts, for tactical positioning and finding targets or points.

Perception. Sight, Hearing and Damage senses, with team affiliation (friend / enemy).

Spawning & coordination. 4 spawner types, and an attack token system that limits how many enemies attack at the same time, so fights stay readable.

Patrol System
Select an AI in the level and a Patrol System section appears in its Details. Level Designers pick the exact points it patrols and set the wait time at each point and its random variation. Two modes: back and forth (A to X, then back through every point) or loop (A to X, then straight back to the start to close the circuit).
Movement fallbacks
Level Designers can also place Target Points for the AI to move to. Without them, it moves freely; if it comes from a spawner, it roams the spawner’s territory to guard it. Every AI has a sensible behaviour, even with no setup.
5 debug tools
  • 3D perceptionUnreal’s default AI Perception debug doesn’t show sight in verticality. My editor tool draws the AI’s full 3D vision and lets Designers edit it, updating in real time.
  • Spawner zonesShows each spawner’s area of action and lets Designers reshape its dynamic NavMesh in real time.
  • Attack tokensShows which AI is about to attack, so the choreography and order of enemy actions in a fight become visible.
  • Last Known PositionShows where each AI last saw its target, to understand and tune its search behaviour.
  • LineOfSight pluginA plugin I implemented: it builds a line of sight dynamically on the ground and returns every actor hit or about to be hit. Placed in an Anim Notify State, it lets Designers set the area of any attack in the animation and see the result in gameplay right away.
Impact
These tools were used constantly by Designers and Level Designers. During sprint reviews, we tuned AI live: areas of action, how readable each attack and behaviour is, animation play rates and how fast Behavior Tree tasks execute, all without asking a programmer for each change.
04Health & progressionGameplay systems
Health

A plug & play health component: added to any actor, it hooks into Unreal’s native damage system and notifies the other systems through dispatchers.

Enemies show a health bar above their head, the player doesn’t. I built it as a dedicated Widget Component class that initialises itself, so nobody has to wire it by hand, and handled the split-screen constraint: a Widget Component in Screen space only renders in player 1’s viewport. It works with several players.

XP curve

Level thresholds follow a quadratic formula (coefficient × level² + base) with named parameters Designers can tune. Large XP gains are processed in a loop, so several level-ups can happen at once, and the threshold of a level is kept separate from the remaining XP.

Why a formula and not a Curve Float? A curve’s extrapolation doesn’t extend a quadratic progression past its last key, so levels beyond it would break. A formula scales to any level.

05Skill card systemCommonUI · UI Programmer
What I did

A complete skill card system in CommonUI, playable with a gamepad or keyboard and mouse: open the menu, reveal 3 cards, confirm one, return to the game.

One state machine. The flow is driven by an enum and a single entry function, and navigation is locked during transitions, so no input can break a sequence halfway.

A confirmation that doesn’t break the layout. The chosen card comes to the foreground over a fade to black. To do it, a proxy card is placed on top through a geometry conversion that stays correct at any DPI, while the real layout stays untouched.

Polish. Focus animations for gamepad and mouse that reverse without visual jumps, plus back-button handling and default focus through Activatable Widgets.

06Architecture & team conventionsMethods & quality
Architecture
Plug & play Actor Components combined with inheritance, 6 Blueprint interfaces, and communication through Event Dispatchers, with attention to hard references and costly casts.
Defensive Blueprint
Programming rules inspired by MISRA, adapted to Blueprint: every reference is validated and fails with an explicit error, never silently; every Switch handles its Default case; no magic values; short single-purpose functions; no dead code.
Encapsulation
Private variables, Pure / Const getters, and gameplay functions that validate, clamp and notify. A deliberate choice between pull (getter) and push (dispatcher).
Written conventions
Naming prefixes, dispatchers prefixed “On”, no collapsed graphs, and a comment colour code (red = deprecated, orange = in progress, green = done). Every system is designed and discussed before it is built.
Built for Designers
Exposed variables grouped in a dedicated category, Data Assets, readable names. Versioned with Perforce streams.
