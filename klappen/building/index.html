01Spawning from inventoryData Table → Preview Actor

One table drives every buildable piece

To spawn the desired structure, I implemented a Data Table–driven system that enables Designers to easily associate meshes and construction data. Based on the enumeration selected in the construction inventory, the system queries the Data Table to retrieve the relevant assets and parameters, which are then assigned to the corresponding preview actor used during the placement phase.

Designer autonomy19 buildable pieces, all defined in the Data Table. My teammates edited it themselves: Roni in particular iterated on the construction pieces and tested them in gameplay straight away, without waiting for me.

02Line trace & snappingValidation

Freedom without friction

The placement system was the most technically demanding part of the project, requiring extensive iteration based on playtesting and game feel feedback. The main challenge was to preserve player freedom while enabling fast, fluid construction chaining.

The system relies on a continuous Line Trace to determine the target placement location in world space. When no valid hit is detected, the preview actor provides immediate visual feedback by switching to an invalid (red) material.

When a valid hit is found, the system first checks for snapping points based on nearby compatible construction actors using BoxCollisions and trace results. If a snapping point is detected, its transform data is extracted and applied directly to the preview actor.

IterationThe first version was too free, so a default grid became necessary. Players then wanted to build in the context of an existing structure, which led to the snapping points. A few pieces still don’t always align the way players expect, but playtesters were satisfied overall, and we learned a lot.

03Grid fallbackVirtual grid

When there is nothing to snap to

If no snapping point is found, a mathematically generated virtual snapping grid is used to calculate the placement transform in world space.

The resulting transform is applied via SetActorTransform, and the preview material is updated to a valid (green) state, indicating that the structure can be placed. This approach allows for precise placement, intuitive snapping and responsive feedback while remaining fully data-driven and scalable.

0490° rotationPlaytest-driven

Less freedom, more fun

The rotation system initially supported full 360° rotation on all axes, providing high freedom but requiring strong 3D spatial awareness from players, which negatively affected usability.

After several playtests, we constrained rotation to 90-degree increments on a single axis (yaw) to improve clarity, grid consistency and placement fluidity.

To preserve flexibility, we created preset variations of similar structures covering alternative orientations on the remaining axes, maintaining visual diversity without reintroducing complexity.

Design decisionPlaytests showed that full 3D rotation cost more in usability than it gave in freedom: one axis, 90° steps, plus preset variants.

05Placement pipelinePlayerController → Player

Two stages, two owners

The construction placement pipeline was divided into two stages.

First, at the PlayerController, the current build mode was evaluated to determine which behavior to execute and to enforce placement constraints, such as limiting spawned instances per input.

Second, within the Player logic, the system retrieved the final transform from the preview actor (world-aligned or snap-based), queried the appropriate entry from the Data Table, and spawned the definitive structure actor into the world. The placement animation was triggered, and the construction loop resumed seamlessly.

In hindsightThe build-mode logic would ideally have been structured as a Switch on Enum–based state system, for better scalability.

06HISM conversionOptimisation

Far away, structures become instances

The conversion of construction actors into Hierarchical Instanced Static Meshes (HISM) quickly became a critical performance optimization as the number of placed structures increased. Each additional actor introduced rendering and tick overhead, significantly impacting performance in large player-built environments.

To address this, I implemented a dedicated “Storage” Blueprint system responsible for serializing placed structures into lightweight data representations (HISM instance data containing transform and type).

Instead of keeping all actors active in the world, the player character uses a Sphere Overlap detection system to monitor nearby constructions. When a structure exits this radius, the original actor is destroyed and immediately replaced by a corresponding HISM instance, dramatically reducing draw calls and actor overhead. At the same time, its data is stored within the Storage system for later reconstruction.

ResultOn long sessions, the more structures players placed, the more FPS dropped, because every one of them stayed loaded and active. With only the structures within interaction range (2,000 Unreal units) kept as full actors, the problem disappeared completely. HISM were chosen so that similar pieces are grouped together, which reduces the cost of each structure even further.

07Re-conversion, no poppingBatched · 0.2 s

The player never sees the swap

When the player moves back within range of structures previously converted into HISM instances, the same Sphere Overlap detection processes each overlapping instance individually and triggers a reconversion function.

This function removes the corresponding HISM instance and respawns its original Blueprint-based actor from the stored serialized data (transform and type). Restoring the Blueprint actor re-enables interactive features such as object-based snapping and the destruction system.

Overlapping instances are first queued, then a 0.2 s looping timer processes the queue in batches. I chose this short delay as a safety margin, so that every structure is fully regenerated before the player can interact with it. As the video shows, the transition stays imperceptible: no visible popping, no functional delay.

VerifiedProfiled with Unreal Insights: the reconversion is invisible to the player and takes very little time.

08Destruction & refundHold to remove

Removing should feel as good as building

The player also has access to a dedicated Destruction Mode, allowing multiple structures to be removed consecutively while refunding their resource cost.

When the mode is activated, the current construction preview data is cached, and a Tick-based Line Trace continuously detects targeted structures. On a valid hit, the structure’s material switches through a Dynamic Material Instance (MID) for real-time visual feedback.

Holding the input past a short timed hold threshold destroys the targeted actor, and a progressive acceleration system shortens the hold for each following destruction, enabling fast chained removals.

TuningEach frame, delta time × Destruct Speed fills the radial gauge on the crosshair; the structure is destroyed once it reaches the threshold. The speed increases with every consecutive destruction, up to a cap, so long removal chains get faster without becoming instant.

Post-mortem

What we believed, what playtests and hindsight showed, and what I would do now.

01Freedom is not creativity
We believed
That total building freedom would unlock the player’s creativity and let them build any house they could imagine.
Reality
Players felt lost rather than free. Rotation had the same problem: free 360° rotation was hard to control, and doing it properly would have meant working with quaternions, which was out of our reach at the time. We quickly realised how heavy a fully free building system is to design, build and learn.
What we did
A mathematical grid that structures snap to automatically, plus 90° steps. It made building much easier to understand and handle.
Trade-off
It also cost freedom: placing a piece on a precise axis became impossible when the grid didn’t allow it.
Next time
Keep the grid as the default, but let the player adjust it in real time (cell size, offset, angle), so precision comes back without bringing confusion with it.
02Optimise for the real need
We believed
That large villages would eventually hurt performance, so we built the HISM conversion ahead of time.
Reality
The system worked and met its goal, but it answered a false need. While trying to anticipate future problems, we didn’t look closely enough at the average length of a play session, which never placed enough structures to require it.
Next time
Profile a realistic session first, then optimise what the data shows. And look at what the engine already offers (World Partition, HLOD, which we didn’t know at the time) before building a custom system.
03Structure the modes early
Reality
Build, destroy, decoration and animal placement were routed through branches in the PlayerController. It worked, but every new mode made the logic harder to read.
Next time
A Switch on Enum state system (or a State Tree) from the start, with one clear entry point per mode.
